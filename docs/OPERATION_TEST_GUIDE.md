# 治理台操作和测试手册

这份给日常使用。你要上线 SQL、改配置、发代码、新增组件，都从这里走，不要绕过平台直接改生产。

## 登录

- 地址：`https://osh.lol/release-console/`
- 账号：`juege`
- 评审账号：`reviewer_a`、`reviewer_b`
- 运维账号：`ops`

密码不要写进文档和聊天记录。生产密码在服务器本地 `.env` 里，变量名是 `OSH_SEED_JUEGE_PASSWORD`。如果忘了密码，走“重置治理台密码”，不要把密码发到群里。

如果页面还是旧的，先强刷浏览器。看到 `组件上线工作台`、`上线前还差这些` 和右侧表格的 `编辑` 按钮，说明前端包已经是新版。

## 一次常规上线怎么走

1. 打开 `Change`。
2. 新建变更单，或者点已有变更单。
3. 在 `组件上线工作台` 选具体动作，比如 `新增 MySQL SQL`、`新增 Kafka Topic`、`新增代码发布`。
4. 填执行内容、回滚内容、风险分析、疑似 bug、验证命令。
5. 点 `加入上线计划` 或 `保存子 change`。
6. 在表格里找到这条上线项，依次点 `分析`、`dry-run`、`执行`、`验证`。
7. 点 `演示确认`，再点 `评审 A 通过`、`评审 B 通过`、`觉哥确认`。
8. 点 `规范校验`、`环境差异`、`announce`、`功能测试`、`数据对比`。
9. 报告都通过后，再点 `切绿`。
10. 生产人工验证没问题后，点 `同步蓝`。
11. 有问题先点 `回蓝`。如果要拆开处理，再按节点 `回滚`。

现在平台默认是安全模式。页面里的执行、切绿、回滚会记录治理证据，不会直接 SSH 去改主业务生产。真要接真实执行器，必须再加白名单和二次确认。

## 上线几条 MySQL SQL

点 `新增 MySQL SQL`。

必填内容：

- 执行 SQL。
- 回滚 SQL。
- 影响表。
- 影响行数预估。
- 幂等判断。
- 验证 SQL。
- 数据量采集口径。

上线前检查：

- SQL 能 dry-run 或 explain。
- 回滚 SQL 能单独执行。
- 课程模块和用户模块是否受影响写清楚。
- 如果影响课程或用户，必须在变更单里明说并让觉哥确认。

回滚方式：

- 先回滚这条 SQL 对应节点。
- 再跑数据量对比。
- 课程和用户模块新增、删除、变化数必须符合变更单说明。

## 新增 ES 索引或别名

点 `新增 ES 索引`。

必填内容：

- index 名。
- mapping。
- settings。
- alias。
- reindex 方案。
- 回切方案。
- 文档数验证命令。

测试重点：

- 新索引能创建。
- alias 能切到新索引。
- 文档数和抽样查询符合预期。
- 回切到旧 alias 可行。

回滚方式：

- 优先切回旧 alias。
- 不要直接删旧索引。
- 新索引确认不用后再清理。

## 修改 ES 配置

点 `新增 ES 配置`。

必填内容：

- 配置文件路径，比如 `elasticsearch.yml` 或 `jvm.options`。
- 配置 diff。
- 滚动重启方案。
- 节点影响范围。
- 回滚配置。
- 健康检查命令。

测试重点：

- green 集群先验证。
- 看 cluster health。
- 看 shard 是否正常。
- 看业务搜索接口是否正常。

## 上线 HBase DDL

点 `新增 HBase DDL`。

必填内容：

- namespace。
- table。
- column family。
- 预分区。
- describe/exists 验证。
- disable/drop 或切旧表回滚方案。

测试重点：

- 先判断表是否已存在。
- 新表 describe 正常。
- 写入和查询样例能跑通。
- 回滚不会误删业务表。

当前 docker 盘点没发现 HBase 容器。真实执行前要先确认 HBase 实例在哪台机器、哪个集群。

## 修改 HBase 配置

点 `新增 HBase 配置`。

必填内容：

- `hbase-site.xml` diff。
- 影响 region 范围。
- 滚动方式。
- 回滚配置。
- 验证命令。

重点看 region 状态和读写延迟。

## 新增 Kafka Topic

点 `新增 Kafka Topic`。

必填内容：

- topic 名。
- 分区数。
- 副本数。
- retention。
- cleanup policy。
- 生产者验证。
- 消费者验证。
- lag 观察方式。

测试重点：

- topic 已创建。
- 分区和副本符合预期。
- 测试生产一条消息。
- 测试消费一条消息。
- 消费组 lag 正常。

回滚方式：

- 先停生产者。
- 确认没有业务还在消费。
- 再按方案删除 topic 或保留空 topic。

## 修改 Kafka 配置

点 `新增 Kafka 配置`。

必填内容：

- broker 配置 diff，或 topic 配置 diff。
- 重启范围。
- lag 观察方式。
- 回滚配置。
- 验证命令。

不要把 Kafka 配置和新增 topic 混成一条。平台里分两条上线项，方便单独回滚。

## 发布 Nacos 配置

点 `新增 Nacos 配置`。

必填内容：

- dataId。
- group。
- namespace。
- 新旧配置 diff。
- 上一版配置。
- 刷新方式。
- 回滚配置。

测试重点：

- 绿环境先发布。
- 应用能读取新配置。
- 配置回滚后应用能恢复。
- 不要把密钥明文写进平台。

## 新增或修改 XXLJob

新增任务点 `新增 XXLJob 任务`。改配置点 `新增 XXLJob 配置`。

任务必填：

- jobHandler。
- cron。
- 路由策略。
- 阻塞策略。
- 默认启停状态。
- 停用回滚方案。

测试重点：

- 手动触发一次。
- 看执行日志。
- 看失败重试策略。
- 回滚时先停任务，再恢复旧配置。

## Redis 变更

脚本或 key 变更点 `新增 Redis 变更`。配置变更点 `新增 Redis 配置`。

必填内容：

- Lua 或 Redis 命令。
- key 前缀。
- TTL。
- 回滚命令。
- key 数量对比。
- 是否影响登录、课程、用户缓存。

测试重点：

- 先在测试环境跑。
- 上线前后 key 数量变化要解释清楚。
- 不要批量删除不带前缀的 key。

## 发布代码

点 `新增代码发布`。

必填内容：

- 仓库。
- 分支。
- commit 范围。
- 构建产物。
- 改动大纲。
- 疑似 bug 分析。
- 风险分析。
- 验证命令。
- 回滚版本。

测试重点：

- 列出接口、页面、定时任务、消息消费变更。
- 说明数据库、Redis、ES、Kafka 是否有配套变更。
- 如果有配套变更，要拆成独立上线项，不要全塞到代码项里。

## 新增组件，比如 MongoDB

点 `新增组件上线`。

必填内容：

- 镜像。
- docker-compose。
- 配置目录。
- 数据目录。
- 端口。
- healthcheck。
- 备份方式。
- 回滚 compose。
- 监控和日志采集。

测试重点：

- 目录规范通过。
- 容器能启动。
- 数据能持久化。
- 停掉再启动数据还在。
- 回滚后服务能恢复。

## 两位评审怎么做

每条上线项都要两个人测。

- 评审 A：通常测测试环境。
- 评审 B：通常复核绿环境。
- 如果开发人也是评审，先点 `演示确认`。
- 紧急上线也要觉哥确认，不能省。

评审证据不要只写“通过”。至少写清楚测了哪个环境、哪个功能、看了什么结果。

## 自动化测试看什么

`功能测试` 看组件和接口是否可用。

`数据对比` 重点看：

- 课程模块新增数。
- 课程模块删除数。
- 课程模块变化数。
- 用户模块新增数。
- 用户模块删除数。
- 用户模块变化数。

没有在变更单里声明时，这些数字应该是 `0`。

`环境差异` 看测试和生产是否有解释得通的差别。

`announce` 看测试环境上线配套是否存在。

## 编辑没反应怎么处理

1. 先强刷浏览器。
2. 打开 `https://osh.lol/release-console/`。
3. 进 `Change`。
4. 右侧表格点 `编辑`。
5. 页面应该滚到 `更新子 change` 表单，并出现 `正在编辑：xxx`。

如果还不行，打开浏览器开发者工具，看接口是否返回 `401`。如果是 `401`，重新登录；如果接口正常但表单没变化，说明前端包可能没更新，重新部署发布包。

## 治理台发版怎么测

治理台每次发版前都要先生成发布包：

```bash
scripts/preflight.sh
scripts/build_release_bundle.sh
scripts/verify_release_bundle.sh release-bundles/osh-prod-release-*.tar.gz
```

测试服验证顺序：

1. 校验 tar 包 sha256。
2. 解包到新目录。
3. 复用服务器本地 `.env`。
4. 跑 `docker compose config`。
5. 启动后看 `/actuator/health`。
6. 登录治理台。
7. 创建小步演示单。
8. 新增一条 MySQL SQL、一条 Nacos 配置、一条 Kafka Topic 和一条代码发布。
9. 每条上线项跑 `分析`、`dry-run`、`执行`、`验证`。
10. 补双评审证据。
11. 跑 `规范校验`、`环境差异`、`announce`、`功能测试`、`数据对比`。
12. 确认报告闸门清空后，再测试 `切绿`、`生产人工验证`、`同步蓝`、`回蓝` 和节点 `回滚`。

这套测试只验证治理台自己的流程，不会直接改生产业务库、网关或真实蓝绿流量。

## 常见卡点

- 登录 401：账号或密码不对，先确认治理台密码，不要改主站账号。
- 切绿被拦：看报告页的 blockers，通常是缺 dry-run、缺执行记录、缺验证记录、缺双评审。
- 数据对比不通过：先看课程和用户模块是否变化。
- 代码项风险分析为空：回到编辑表单补完整，再保存。
- 新组件规范不通过：补配置目录、数据目录、compose、healthcheck 和回滚方案。

## 重置治理台密码

不要在聊天里贴密码。推荐做法是让运维在生产服务器本地重置，或者让 Codex 通过交互 SSH 操作，但不要把新密码打印到日志里。

如果只是查看部署时配置的种子密码，在生产服务器上看 `.env`，常见路径是：

```bash
cd /opt/osh-prod-release-new
grep '^OSH_SEED_JUEGE_PASSWORD=' .env
```

注意：种子密码只在用户首次创建时写入。用户已经存在时，改 `.env` 不一定会改数据库里的登录密码。忘记登录密码时，按重置流程处理。

## 最短测试流程

只想确认平台能不能用，按这个来：

1. 登录 `juege`。
2. 进 `Change`。
3. 点一条已有变更单。
4. 点第一条上线项右侧 `编辑`。
5. 改一行测试计划，点 `保存子 change`。
6. 点这条上线项的 `分析`、`dry-run`、`执行`、`验证`。
7. 点 `规范校验`、`环境差异`、`announce`、`功能测试`、`数据对比`。
8. 看报告页 blockers 是否清空。

这套测试只写治理库记录，不会改主业务库。
