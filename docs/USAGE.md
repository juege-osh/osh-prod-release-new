# OSH 上线治理台操作说明

这份文档是给日常上线、演练、回滚和排障用的。目标很简单：让人一眼知道该点哪里、该看什么、出了问题该退到哪一步。

## 1. 先认清环境

- `osh-test`：`43.242.200.25:58753`
- `osh-prod`：`149.88.92.159:16328`
- 测试环境域名：`https://juegeresource.top/`
- 生产环境域名：`https://osh.lol/`
- 治理台推荐入口：`https://osh.lol/release-console/`

## 2. 默认账号

治理台默认账号只用于演练和管理，不要拿去当真实业务账号。

- 觉哥：`juege`
- 评审 A：`reviewer_a`
- 评审 B：`reviewer_b`
- 运维：`ops`

密码不在文档里重复写，按本机启动环境变量或种子配置来。

## 3. 进入系统

1. 打开治理台。
2. 输入账号密码登录。
3. 进入后先看总览页，确认环境、组件和当前变更单状态正常。

如果页面打不开，先确认：

- 生产反代是否指向 `/release-console/`
- 后端是否监听 `127.0.0.1:18080`
- 前端是否监听 `127.0.0.1:18081`
- 你访问的是治理台，不是主站首页

## 4. 新建变更单

1. 打开 `Change` 页。
2. 点 `新建演练单`。
3. 系统会自动拉起默认组件范围：
   - MySQL
   - Redis
   - Nacos
   - Kafka
   - Elasticsearch
   - HBase
   - Java 后端
   - Vue 前端
   - Nginx
   - Docker Compose
   - MongoDB
4. 负责人更新每个子 change 的内容、增量计划、回滚计划、测试计划和数据采集计划。

建议新建时就把下面几项填实：

- 上线内容
- 依赖关系
- 回滚顺序
- 数据采集范围
- 是否需要演示确认

## 4.1 新增真实上线项

变更单建好后，不是只能用默认组件。你可以继续点：

- `新增 SQL`：粘贴要上线的 SQL、回滚 SQL、影响行数、验证 SQL。
- `新增配置`：粘贴 Nacos/Nginx/Compose 等配置 diff、目标文件路径、回滚配置。
- `新增代码`：填写分支、commit 范围、构建产物、代码改动大纲、疑似 bug 和风险分析。

每个上线项都会变成独立子 change 和上线节点，可以单独评审、单独测试、按顺序上线，也可以按节点回滚。同一个组件可以有多条上线项，比如默认 MySQL 组件项之外，再追加三条 SQL；平台会按节点顺序绑定，不会把新 SQL 覆盖到旧 MySQL 节点上。

实际操作时按这个顺序来：

1. 新建变更单。
2. 点 `新增 SQL`、`新增配置` 或 `新增代码`。
3. 填执行内容、回滚内容、风险分析、疑似 bug 分析和验证命令。
4. 保存后看表格，确认多了一条独立上线节点。
5. 点单项的 `分析`，让平台生成改动大纲、风险点、疑似 bug 和验证清单。
6. 点单项的 `dry-run`，记录只读检查或演练结果。
7. 点单项的 `执行`，记录绿环境执行证据。安全模式下不会直接改生产。
8. 点单项的 `验证`，记录绿环境验证结果。
9. 补两位评审人的测试证据。
10. 跑规范、功能、数据、环境差异和 announce。
11. 全部通过后才允许切绿。

现在切绿闸门会检查每个上线项。缺 `dry-run`、缺执行记录、缺验证记录，都会被后端拦住。

SQL 上线项至少要填：

- SQL 执行内容。
- SQL 回滚内容。
- 影响表和影响行数预估。
- 幂等判断。
- 数据量采集口径。
- 课程模块、用户模块是否受影响。

配置上线项至少要填：

- 配置路径或配置 key。
- 新旧配置 diff。
- 配置校验命令。
- 回滚配置。
- 影响服务和刷新方式。

代码上线项至少要填：

- 分支和 commit 范围。
- 代码改动大纲。
- 可能的 bug 点。
- 风险分析。
- 构建产物。
- 验证命令和回滚版本。

## 5. 三种视图

变更详情页里有三种看法：

- 表格：看顺序、负责人、规范、双评审和回滚顺序
- 树：看组件层级和目录路径
- 图：看整条上线链路

平时排查问题，先看表格。想看顺序和依赖，再切树和图。

## 6. 双人评审

每个子 change 必须至少两位评审人通过。

推荐流程：

1. 先由开发人更新子 change 内容。
2. 如果开发人也参与评审，先做一次演示确认。
3. 评审 A、评审 B 分别提交通过。
4. 紧急上线还要再过觉哥确认。

页面上有这些动作：

- `演示确认`
- `评审 A 通过`
- `评审 B 通过`
- `觉哥确认`

## 7. 演示确认

如果某个上线内容是开发人自己参与评审，先点 `演示确认`。

它的作用很直接：

- 记录开发人向另一位评审做过演示
- 作为后续审批和责任追溯证据
- 避免“人看过了，但没人敢担责”的情况

## 8. 组件规范校验

每个组件都要满足：

- 配置目录
- 数据目录
- 部署目录
- 增量脚本
- 回滚脚本
- 健康检查
- 数据采集口径

点 `规范校验` 后，系统会检查这些字段是否齐全。

## 9. 自动化测试

### 功能测试

点 `功能测试` 后会检查：

- MySQL
- Redis
- Nacos
- Kafka
- Elasticsearch
- HBase
- Java 接口
- Vue 入口
- Nginx
- Docker Compose

### 数据量对比

点 `数据对比` 后会生成摘要报告，重点看：

- 课程模块是否变化
- 用户模块是否变化
- 治理台自己的演练数据是否变化

正常情况下，课程模块和用户模块的新增、删除、修改都应该是 `0`。

### 环境差异

点 `环境差异`，看测试环境和生产环境的差别：

- 测试环境通常是单套部署
- 生产环境是蓝绿治理
- 这类差异要能解释清楚

### announce 检查

点 `announce`，检查测试环境有没有对应文件或标记。

这一步的意思是：正式上线前，先确认测试环境的上线配套没缺。

## 10. 切绿和回蓝

### 切绿

只有在以下步骤都完成后，才可以切绿：

- 组件规范通过
- 两位评审证据齐了
- 功能测试通过
- 数据量对比通过

切绿后：

- 先让绿系统承接上线内容
- 再做生产人工验证

### 回蓝

如果切绿后发现问题，立即回蓝。

回蓝的目标是：

- 先恢复稳定面
- 再慢慢查问题
- 不要把排障和上线动作混在一起

## 11. 生产人工验证

切到绿系统后，负责人要在生产上做一次人工验证。

建议验证清单：

- 页面能打开
- 接口能返回
- 关键组件能连通
- 没有误写课程模块和用户模块

验证通过后，再点同步蓝系统。

## 12. 按节点回滚

如果需要回滚，不要一把梭回整个系统，按节点来。

推荐顺序：

1. 先回最新改动的应用层
2. 再回网关和前端
3. 再回中间件配置
4. 最后回基础组件

回滚前先看：

- 变更单里的 rollback 顺序
- 回滚脚本
- 影响范围
- 课程模块和用户模块是否会被碰到

## 13. 常规上线和紧急上线

### 常规上线

常规上线需要：

- 组内两人审核通过
- 觉哥最终确认

### 紧急上线

紧急上线需要：

- 组内两人审核通过
- 觉哥确认

紧急上线不能省掉责任链。

## 14. 报告怎么看

报告页主要看四块：

- 组件规范
- 功能测试
- 数据量对比
- 环境差异和 announce

重点看两件事：

- 数据改动是否和上线内容一致
- 课程模块、用户模块有没有被误伤

## 15. 排障顺序

如果页面出问题，按这个顺序查：

1. 先看浏览器有没有进错域名
2. 再看前端是否还在
3. 再看后端 health
4. 再看数据库和迁移
5. 最后看反代配置

如果是流程卡住，优先看：

- 变更单状态
- 双评审是否齐
- 演示确认是否补了
- 功能测试和数据对比是否通过

## 16. 安全提醒

- 不要在日志里打印密码、token、数据库连接串
- 生产默认只读
- 真写操作、切流、回滚前先确认
- 课程模块和用户模块要单独盯紧

## 17. 一句话流程

新建变更单 -> 补子 change -> 双评审 -> 演示确认 -> 规范校验 -> 功能测试 -> 数据对比 -> 切绿 -> 人工验证 -> 同步蓝 -> 出问题就回蓝或按节点回滚
