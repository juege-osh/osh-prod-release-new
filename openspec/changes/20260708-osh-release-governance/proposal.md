# Proposal: osh-release-governance

## 背景

OSH 现在需要一套自己的上线治理系统，不能只靠口头协调。发布时要能看清楚每个组件的顺序、责任人、测试结果、数据差异和回滚路径，还要能把蓝绿切换、双人评审和人工复核串起来。

## 目标

- 管理主项目 `osh-backend/release/20260708` 和 `osh-frontend/release/20260708` 的发布元数据。
- 支持变更单、组件树、发布节点、审批、演示确认、功能测试、数据对比、蓝绿切换和回滚。
- 支持新增组件类型，比如 MongoDB。
- 支持常规上线和紧急上线两种流程。
- 提供可直接使用的 Vue 管理界面。
- 提供可部署的 Java 后端。

## 非目标

- 不直接改造主项目 `osh-backend` 和 `osh-frontend` 的业务代码。
- 不直接写死生产数据库里的业务数据。
- 不在这次变更里实现完整的远程运维平台代理。

## 关键规则

- 每个上线内容至少 2 个评审人。
- 如果评审人 A 也是开发人，A 要先向 B 做一次演示确认。
- 常规上线需要组内两人审核后，再由觉哥最终确认。
- 紧急上线需要组内两人审核后，再加觉哥确认。
- 任何发布都要支持按节点回滚。
- 蓝绿切换只允许先操作绿环境，确认后再切回蓝环境。
- 自动化测试要给出功能结果、数据量差异和 AI 汇总判断。

## 用户价值

- 上线前能看懂会改什么。
- 出问题时能快速定位到人和节点。
- 回滚不再是整机瞎退。
- 测试环境和生产环境的差异更容易查。

## 风险

- 流程太复杂会拖慢页面实现，所以先做可用版本，再补自动化细节。
- 如果数据模型设计太散，后面不好扩展，所以先把组件、变更、审批、报告四块分开。
